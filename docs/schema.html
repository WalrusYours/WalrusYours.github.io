Schema

What a schema is

The schema is a single YAML file, schema.yml, that tells WALRUS about your platform. It is written once by your developers, kept in your own repository, and pushed to WALRUS. WALRUS never reads your database and never fetches the file itself.

Why a schema

  • One engine, any content. A shop, a music service and a news site have different data and different ideas of a good result. With a schema the same engine serves all of them, and adopting WALRUS is a push of a file: no code change, no rebuild, no database migration.
  • A contract. WALRUS checks the schema before accepting it and reports every problem at once, so mistakes surface when you push, not when users see bad results. Unknown keys and undeclared attributes are rejected, which catches typos.
  • Control with limits. The author decides what can be weighted. The end user decides how much, through the few knobs the author chose, and can never go outside the schema.
  • Explanations for free. Every score is a sum of declared signals, so the breakdown that produced a ranking can explain it.
  • Safe change over time. Every accepted schema is stored as a version. WALRUS says whether a change is additive (applies live) or breaking (stored data must be rebuilt) before anything changes.

Anatomy

A schema has up to eight top-level keys. Only the first five are always needed.

version: 1
entities:     { ... }   # what exists
interactions: { ... }   # what users do
similarity:   { ... }   # how things are compared
signals:      { ... }   # how a score is built
knobs:        [ ... ]   # what the end user can move
presets:      { ... }   # named knob positions
constraints:  [ ... ]   # hard rules
recommendable: post     # which entity is ranked

The parser rejects unknown keys, so a typo such as halflife is an error instead of a silently ignored rule. Names you invent (entities, attributes, interactions, signals, knob ids, presets) must match ^[a-z][a-z0-9_]*$, because they end up in database labels and property names.

version is an integer of at least 1. It is the version of the schema language, not of your schema; WALRUS numbers your pushes itself.

entities

Declares what exists and which attributes you will send. Anything not declared is rejected at ingest. An entity named user is required, because constraints and signals refer to $user. 

entities:
  post:
    key: id
    attributes:
      topic:      { type: categorical }
      created_at: { type: timestamp }
KeyMeaning
keyThe name of the id field, normally id. Required.
attributesThe fields you will send, each with a type.
typecategorical (a small set of labels such as a topic), string (free text), float, int, bool, timestamp, set (a list of strings such as tags), vector (an embedding), ref (the id of another entity), geo (a point, sent as {"lat": 47.01, "lon": 28.86}).
ofFor set: the element type, currently string.
entityFor ref: which entity it points to, for example { type: ref, entity: user }.
dimFor vector: the number of dimensions.
rangeFor float and int: [min, max], min below max. Values outside are rejected.
optionalThe attribute may be missing. Every other attribute must be present.
sensitiveCounts in scoring and constraints but is never named in a reason.
computedAn expression over the entity's other attributes, evaluated at ingest, for example "len(title)". You never send a computed attribute. Cycles are rejected.

interactions

Turns events into weighted edges that fade over time. A like is a stronger statement than a view; a dislike is a negative one. 

interactions:
  view: { weight: 1.0, value: seconds, transform: log1p, half_life: 3d }
  like: { weight: 4.0, half_life: 30d }
KeyMeaning
weightHow strongly the event counts. Negative means the user dislikes the target.
valueThe name of a number your event carries (seconds viewed, fraction listened). Omit it for plain yes/no events. The number is sent as value on the event.
transformTurns that number into a bounded contribution: identity, log1p, sqrt, clamp, or an expression in v, for example "1 - min(v, 30) / 30". Needs value.
half_lifeHow long until an event counts half as much, for example 3d. Omit it for no decay.
targetThe entity the event points at, when it is not the recommendable one.
lockedAn editing guard for the dashboard. It is not access control.

Durations use s, m, h, d, w.

similarity

Defines how two items, or two users, are compared. It is a map from entity name to a list of terms; the scores of the terms are combined using their weights. The neighbour signals read the result. 

similarity:
  post:
    - { on: topic, metric: equals,  weight: 0.5 }
    - { on: tags,  metric: jaccard, weight: 0.5 }
  user:
    - { via: interactions, metric: cosine }
KeyMeaning
onThe attribute (or list of attributes) to compare.
via: interactionsCompare users by their interaction history instead of by attributes. Use it for user. A term uses on or via, never both.
metricequals (same value), jaccard (overlap of two sets), cosine (angle between vectors or number lists), log_ratio (closeness of two positive numbers such as prices), closeness (one number: one minus the gap as a share of the range, for a feature like energy).
weightThe term's share in the combined similarity. Must be above 0 for on terms.

signals

The named parts of a score. The score of an item for a user is the weighted sum of the signals, using the current weights. The type picks a built-in behaviour and the other keys configure it. default is the weight when the user has touched no knob. 

signals:
  content: { type: item_neighbors, default: 0.5 }
  recency: { type: age_decay, default: 0.3, on: created_at, half_life: 2d }
TypeRewardsRanks today
item_neighborsItems similar to what the user already engaged with.yes
user_neighborsItems that users with a similar history engaged with.yes
global_countPopularity over a window, for example 7d. Size, not speed.yes
age_decayFresh items. Needs on: <timestamp attribute> and a half_life.yes
low_exposureItems few people have seen, for discovery.yes
embeddingA taste the attributes do not capture, learned from who interacted with what. Needs training.yes
co_occurrence, attribute_target, context_match, provided, proximityItems that appear together in playlists or baskets; closeness to a target value; a match with the request's context; scores your platform supplies; nearer places.yes
trendItems whose recent engagement is well above their ordinary pace: acceleration, not size.not yet
own_historyItems the user has seen before, without a hard exclusion.not yet
attribute_matchItems whose attribute matches a user value, against: "$user.<attribute>".not yet
diversity_rerankSpreads results over the values of an attribute so one author cannot fill the feed.not yet

A signal the engine cannot score yet is skipped, never fatal, and the push lists it under warnings. Using an existing signal type is only configuration. A brand-new type is code, registered in the signal registry; that is the one thing a schema push cannot do.

knobs and presets

Knobs are the only controls the end user ever sees. Each one is a projection onto one or more signal weights, so you decide what can be weighted and the user decides how much. 

knobs:
  - id: explore
    label: "Safe picks  <->  Surprise me"
    range: [0, 1]
    maps: { exploration: "x", author_spread: "0.3 + 0.5 * x" }

presets:
  default:  { taste_vs_crowd: 0.5, explore: 0.2 }
  discover: { explore: 0.9, taste_vs_crowd: 0.8 }
KeyMeaning
idA stable identifier, unique among knobs.
labelPlain-language text shown to users. Required. Write both ends of the slider.
range[min, max] of the slider, min below max.
mapsWhere the knob acts. Each key is a signal id or a meta-parameter, each value an expression in x, the knob position.

The meta-parameter interactions.half_life_scale stretches or shrinks every half-life, which gives a "this week versus all-time" knob: maps: { interactions.half_life_scale: "lerp(0.2, 4, x)" }.

Expressions use numbers, x, + - * /, comparisons, && || !, and the functions min, max, abs, round, sqrt, log1p, clamp(x, lo, hi), lerp(a, b, t) and if(cond, a, b). They are compiled once when the schema loads, so moving a slider never parses anything. Division by zero gives 0.

A preset is a named set of knob positions the user can pick in one tap. It sets knobs, not signals, and every value must lie inside the knob's range.

constraints

Hard rules, applied before scoring. They are never weighted, and no knob can override them. Each is a require or an exclude with one condition: 

constraints:
  - require: { attribute: status, equals: active }
  - exclude: { interacted: [dislike] }
  - exclude: { interacted: [skip], count_gte: 3, within: 30d }
  - exclude: { attribute: seller_id, in: "$user.blocked_sellers" }
  - require: { attribute: age, gte: "$user.min_age" }
  - require: { attribute: location, within_km: 15, of: "$context.location" }
KeyMeaning
require / excludeKeep only items that match, or drop the items that match.
attributeTest an attribute of the recommendable entity, with one of equals, in, gt, gte, lt, lte, contains. The right side may read $user.<attribute>, $context.<field> or $seed.<attribute>.
within_km, ofThe attribute is a geo point at most this many kilometres from the place of.
interactedTest the user's history instead: a list of interaction names. With count_gte and within to ask for a number of events in a period.
whenApply the constraint only if this expression is true, for example "$user.explicit_allowed == false".

A condition that reads something the request does not have (no seed items, a user attribute the user does not have, a context field that was not sent) does not apply, so missing data never empties a list. recommendable names the entity that is ranked; it can be left out when exactly one entity besides user is declared.

Beyond the basics

The sections above are enough for a feed. A schema can also declare several recommenders with their own seeds (an item, a playlist or basket, a session, a group), request context, business rules such as per-seller caps, and computed attributes. The examples below cover them.

Pushing a schema

The schema is pushed to WALRUS and never pulled. Every push goes through the same steps:

  1. Parse. The YAML is decoded into typed structures. Unknown keys fail here, and so do an empty or malformed document and a body over the size limit.
  2. Validate. References and types are checked: every ref points at a declared entity, signal types and metrics exist, an age_decay signal points at a timestamp, every knob maps to a declared signal with a valid expression, presets stay inside knob ranges, constraints name real attributes and interactions. All problems come back together as a list of {path, message} with status 400.
  3. Diff. The new schema is compared with the active one. Adding things, or changing weights, labels, knobs, presets or similarity, is additive and applies live. Removing an entity, attribute, interaction or signal, or changing a type, is breaking. A breaking change without ?confirm_breaking=true returns 409 with the diff and changes nothing. An identical schema creates no new version.
  4. Record. An accepted schema becomes the next version, stored with its number, a hash, the author, the time and the YAML. GET /v1/schema returns the active one and GET /v1/schema/history lists every version.
  5. Activate. It is compiled in memory (knob maps and transforms become functions) and replaces the old one atomically, so a request sees the old schema or the new one, never a mix.
curl -X PUT -H "Authorization: Bearer $WALRUS_ADMIN_KEY" \
     --data-binary @schema.yml "$WALRUS_URL/v1/schema?dry_run=true"   # check, change nothing
curl -X PUT -H "Authorization: Bearer $WALRUS_ADMIN_KEY" \
     --data-binary @schema.yml "$WALRUS_URL/v1/schema"                # apply

A push never needs a code change, a rebuild or a restart. Three ways to get the file there:

  • CI (recommended). Keep schema.yml in your repository. Run a dry run on every pull request as a gate and push for real on merge.
  • Boot sync. Your backend pushes the schema at startup. An unchanged schema creates no new version, so this is safe on every start.
  • Manual. curl or the dashboard, for experiments.

After a breaking change, re-import the affected entities and events so stored data matches the new schema; the 409 response says what is required.
