Get started

Introduction

WALRUS is a recommendation engine you adapt to your platform with one YAML file. You describe your data and how a good result is scored; end users get a few knobs to re-weight the ranking, and every result comes with the reasons it was shown.

How it fits together

WALRUS runs next to your backend, as its own service. It never reads your database: you push it a schema, then entities and events, and ask it for ranked lists. 

# your end-user client never talks to WALRUS
client  ->  your app server  ->  WALRUS  ->  Neo4j
                  |                  ^
                  +-- schema, entities, events, recommend requests
  • The platform decides what can be weighted. The schema declares the signals a score is built from, their default weights and the few knobs users may move.
  • The user decides how much. A knob is a projection onto signal weights. The user can never reach outside what the schema allows.
  • Hard rules come first. Constraints filter candidates before scoring and no knob can override them.
  • Re-ranking is instant. Candidates and similarities do not depend on weights, so they are computed once and kept. Moving a slider only re-scores.
  • Every result is explainable. A score is a sum of declared signals, so the breakdown that produced it is the explanation.

Your servers call WALRUS with an API key. Keep the key on your backend: an end-user client calls your backend, never WALRUS.

Install

You need Docker with the Compose plugin. One command installs Neo4j, the engine and the admin dashboard, generates the admin key and the database password, and waits until they are healthy: 

curl -fsSL https://raw.githubusercontent.com/WalrusYours/WalrusCore/main/install.sh | bash

It installs into /opt/walrus (as root) or ~/walrus, prints the admin key once, and serves the dashboard on http://127.0.0.1:3001. That address is loopback only: put a reverse proxy or an SSH tunnel in front of it. Run the command again to upgrade; it keeps your .env and pulls the newest images.

To do it by hand, copy docker-compose.yml and .env.example (as .env) from the repository and run docker compose up -d.

SettingWhat it does
WALRUS_ADMIN_KEYThe key for every API call and the dashboard sign-in. The engine refuses to start without one.
NEO4J_PASSWORDThe database password, at least 8 characters. Applied when the volume is first created.
WALRUS_PORTThe engine's port, 8080 by default, bound to 127.0.0.1 unless you set WALRUS_BIND.
WALRUS_TRAIN_INTERVALOptional. Retrain learned models on a schedule, for example 15m.
WALRUS_INSTANCE_NAMEOptional. A name shown on /health and in the dashboard.

Development defaults are public. Without a .env Compose uses a well-known key and password so it starts with no setup. Set your own for anything that is not a local try-out.

Check that it is up. Health is the one endpoint that needs no key:

curl http://127.0.0.1:8080/health
{"instance_id":"f6f1595e...","instance_name":"walrus","status":"ok","version":"0.0.0-dev"}

Quickstart

Five calls take you from an empty engine to a ranked, explained feed. The example is a small social feed of posts. Set these once; every call below uses them: 

export WALRUS_URL=http://127.0.0.1:8080
export WALRUS_ADMIN_KEY=<the key the installer printed>

1. Push a schema

Save this as schema.yml. It is a complete, valid schema, and the next page explains every key in it.

version: 1

entities:
  user:
    key: id
    attributes:
      interests: { type: set, of: string, optional: true }
  post:
    key: id
    attributes:
      topic:      { type: categorical }
      tags:       { type: set, of: string }
      created_at: { type: timestamp }
      status:     { type: categorical }

interactions:
  view: { weight: 1.0, value: seconds, transform: log1p, half_life: 3d }
  like: { weight: 4.0, half_life: 30d }

similarity:
  post:
    - { on: topic, metric: equals,  weight: 0.5 }
    - { on: tags,  metric: jaccard, weight: 0.5 }

signals:
  content:     { type: item_neighbors, default: 0.6 }
  popularity:  { type: global_count,   default: 0.2, window: 7d }
  recency:     { type: age_decay,      default: 0.3, on: created_at, half_life: 2d }
  exploration: { type: low_exposure,   default: 0.1 }

knobs:
  - id: explore
    label: "Safe picks  <->  Surprise me"
    range: [0, 1]
    maps: { exploration: "x", content: "1 - 0.5 * x" }

presets:
  default: { explore: 0.2 }

constraints:
  - require: { attribute: status, equals: active }

recommendable: post

Check it first with a dry run, which reports every problem and the diff without changing anything, then push it for real:

curl -X PUT -H "Authorization: Bearer $WALRUS_ADMIN_KEY" \
     --data-binary @schema.yml "$WALRUS_URL/v1/schema?dry_run=true"

curl -X PUT -H "Authorization: Bearer $WALRUS_ADMIN_KEY" \
     --data-binary @schema.yml "$WALRUS_URL/v1/schema"
# {"ok":true,"errors":[],"diff":{"verdict":"additive",...},"version":1,"message":"applied as version 1"}

2. Send entities

Users and posts, in one batch. Each one is checked against the schema.

curl -X POST -H "Authorization: Bearer $WALRUS_ADMIN_KEY" "$WALRUS_URL/v1/entities" -d '{"entities":[
  {"entity":"user","id":"u_1","attributes":{}},
  {"entity":"post","id":"p_1","attributes":{"topic":"cycling","tags":["road","gear"],"created_at":"2026-10-05T09:00:00Z","status":"active"}},
  {"entity":"post","id":"p_2","attributes":{"topic":"cycling","tags":["road","race"],"created_at":"2026-10-06T08:00:00Z","status":"active"}},
  {"entity":"post","id":"p_3","attributes":{"topic":"cooking","tags":["pasta"],"created_at":"2026-10-06T07:00:00Z","status":"active"}}
]}'
# {"accepted":4,"rejected":[]}

3. Send events

What the user did. The value is the number the event carries, here the seconds viewed, which the schema's transform turns into a bounded contribution. Send the time the event happened, not the time you send it: decay is computed from it. 

curl -X POST -H "Authorization: Bearer $WALRUS_ADMIN_KEY" "$WALRUS_URL/v1/interactions" -d '{"interactions":[
  {"user":"u_1","type":"like","target":"p_1","ts":"2026-10-05T10:00:00Z"},
  {"user":"u_1","type":"view","target":"p_1","ts":"2026-10-05T09:58:00Z","value":42}
]}'
# {"accepted":2,"rejected":[]}

4. Recommend, and move a knob

Ask for a list for the user. Then ask again with the knob at each end. Only the weights change, so the second call reuses everything else and re-scores. 

curl -H "Authorization: Bearer $WALRUS_ADMIN_KEY" "$WALRUS_URL/v1/recommend/u_1?limit=3&knobs.explore=0"
# items: p_1 1.20, p_2 0.97, p_3 0.28    weights: content 1, exploration 0

curl -H "Authorization: Bearer $WALRUS_ADMIN_KEY" "$WALRUS_URL/v1/recommend/u_1?limit=3&knobs.explore=1"
# items: p_2 1.63, p_3 1.28, p_1 0.70    weights: content 0.5, exploration 1

The response also carries the final weights that were applied and a rec_id:

{
  "recommender": "default",
  "rec_id": "rec_c4b5e035cc18cf19",
  "items": [
    { "id": "p_2", "type": "post", "score": 1.5 },
    { "id": "p_3", "type": "post", "score": 1.085 },
    { "id": "p_1", "type": "post", "score": 0.8 }
  ],
  "weights": { "content": 0.6, "exploration": 0.8, "popularity": 0.2, "recency": 0.3 },
  "knobs": { "explore": 0.8 },
  "candidates_considered": 3,
  "took_ms": 0
}

Your app turns the ids into posts from its own database and renders them. Add "explain": true to a POST body to get a one-line reason on every item.

5. Explain an item

Why is p_2 first? Ask about that exact list by its rec_id. It is kept for one minute.

curl -H "Authorization: Bearer $WALRUS_ADMIN_KEY" "$WALRUS_URL/v1/recommendations/rec_c4b5e035cc18cf19/explain/p_2"
{
  "item": "p_2", "position": 1, "score": 1.5,
  "breakdown": [
    { "signal": "exploration", "value": 0.8, "because": "Nobody has played or added it yet" },
    { "signal": "content",     "value": 0.4, "because": "Same topic as p_1" },
    { "signal": "recency",     "value": 0.3, "because": "Released in 2026" },
    { "signal": "popularity",  "value": 0 }
  ],
  "weights_used": { "content": 0.6, "exploration": 0.8, "popularity": 0.2, "recency": 0.3 }
}

The values add up to the score. The explanation is the computation, not a story told afterwards.
