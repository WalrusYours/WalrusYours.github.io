API

API reference

Everything is under /v1 and JSON, except the schema, which is YAML. /v1 only ever gains things: nothing you build against it is removed.

Overview

Send Authorization: Bearer <admin key>, the key the engine was started with in WALRUS_ADMIN_KEY. Only the health endpoints are open. Scoped keys and per-tenant keys are not built yet. Call WALRUS from your backend or CI, never from a browser.

Errors always have one shape:

{ "error": { "code": "validation_error", "message": "unknown knob \"nope\"" } }
Method and pathWhat it does
GET /health, GET /v1/healthLiveness: status, version, instance_id, instance_name. No key.
PUT /v1/schemaPush the YAML schema as the request body. ?dry_run=true validates and returns the diff without applying; ?confirm_breaking=true applies a breaking change. 200 applied, 400 with the path of every problem, 409 when breaking and unconfirmed. An accepted schema can return warnings: what it asks for that the engine does not do yet.
GET /v1/schemaThe active schema: yaml, version, hash. 404 before the first push.
GET /v1/schema/historyEvery pushed version.
POST /v1/entitiesUp to 1000 entities (items, users...). Each is checked against the schema; bad ones are listed in rejected and the rest are stored.
PUT /v1/entities/{type}/{id}Create or replace one entity: {"attributes": {...}}. 201 when new, 200 when replaced, 400 with the reason when it breaks the schema.
GET /v1/entities, GET /v1/entities/{type}/{id}How many entities of each type are stored, and one entity back.
POST /v1/importLoad a whole catalogue as JSON Lines, one {"entity", "id", "attributes"} per line. Reports the first 100 bad lines by number.
POST /v1/interactionsUp to 1000 events, checked against the schema's interactions. GET /v1/interactions counts them by type.
GET /v1/recommend/{user}The shorthand: the implicit default recommender for a user. Takes ?limit=, ?preset= and ?knobs.<id>=<number>.
POST /v1/recommend/{user}The same, with a JSON body (for example exclude).
POST /v1/recommenders/{recommender}/recommendRecommend with a recommender the schema declares.
GET /v1/recommendations/{rec_id}/explain/{item}Why one item is where it is in one earlier list.
POST /v1/models/train, GET /v1/modelsTrain the learned-taste models in the background (202, 409 if a run is going), and see each model against the schema and the last run.
POST, GET, DELETE /v1/admin/sessionSign in with {"key": "..."} and get a short-lived HttpOnly cookie, check it, sign out. Used by the dashboard so the key is never kept in a browser.

Entities and events

Entities

Entities are checked against the pushed schema: the type and every attribute must be declared, each value must have the declared type (and range), and every attribute that is not optional must be present. Sending the same type and id again replaces the entity, so loads can be repeated. 

POST /v1/entities

{ "entities": [
  { "entity": "track", "id": "back_in_black", "attributes": { "energy": 0.92, "genres": ["rock"] } }
] }
{ "accepted": 1, "rejected": [
  { "index": 3, "entity": "track", "id": "x", "error": "attribute \"energy\": 1.5 is outside the range [0, 1]" }
] }

To load a whole catalogue, POST /v1/import takes JSON Lines, one entity per line. The import is idempotent: running it again with the same ids updates rather than duplicates.

Interactions

Send every event type you declared in the schema, and nothing else. Undeclared types and fields are rejected, per event, without failing the batch. 

POST /v1/interactions

{ "interactions": [
  { "user": "u_1", "type": "view", "target": "p_1", "ts": "2026-10-05T09:58:00Z", "value": 42 },
  { "user": "u_1", "type": "like", "target": "p_1", "ts": "2026-10-05T10:00:00Z" }
] }
FieldMeaning
user, targetThe ids of the user and of the entity acted on.
typeOne of the schema's interactions.
tsWhen the event happened, not when you send it. Decay is computed from it.
valueThe number the event carries, when the schema declares value: for it.
fieldsExtra values, only those the interaction declares under fields:.

Do not call WALRUS from request handlers synchronously. Forward events in batches from a queue or an analytics hook; a few seconds of lag does not change recommendations. If WALRUS is down, buffer and retry. Send item creates, updates and status changes too, or new items never enter the candidate pool and constraints see stale data.

Recommend

For a schema with no recommenders, GET /v1/recommend/{user} is all you need. A schema that declares its own recommenders names the one to run in the path. The schema decides what a recommender takes: seed: is one of user, item, items, session, users or none, and the request carries exactly that field. 

POST /v1/recommenders/playlist_add/recommend
Authorization: Bearer <admin key>

{
  "items": ["back_in_black", "thunderstruck", "enter_sandman"],
  "limit": 5,
  "knobs": { "vibe_vs_branch_out": 1 },
  "explain": true
}
FieldMeaning
user, item, items, session, usersThe seed. Only the one the recommender's seed: names is accepted, otherwise 400 seed_mismatch.
contextValues for the schema's context block (device, time of day...). Unknown fields are rejected; hour, weekday and month are filled in by the engine.
limitCapped by the recommender's limit.max; defaults to limit.default (30 and 200 when the schema says nothing).
excludeItem ids to leave out. Pagination is stateless: send the ids already shown.
knobsThe end user's values by knob id. Only knobs the recommender offers; others are 400. They apply to this request and are not saved.
presetA named preset from the schema.
explaintrue adds a one-line reason to each item.
scoresPer-item scores your platform supplies for signals of type provided.
 
{
  "recommender": "playlist_add",
  "used": "playlist_add",
  "rec_id": "rec_1a7751f9b1bde656",
  "items": [
    { "id": "paranoid", "type": "track", "score": 0.678,
      "reason": "Often added to playlists with Back in Black · Shares rock and hard rock with Thunderstruck" }
  ],
  "weights": { "co_listed": 0.4, "sounds_like": 0.0, "exploration": 0.3 },
  "knobs": { "vibe_vs_branch_out": 1 },
  "experiment": { "id": "trend_weight", "variant": "control" },
  "candidates_considered": 13,
  "took_ms": 1.2
}
  • used differs from recommender when a fallback answered, for example an empty playlist falling back to one that reads its title.
  • weights are the final numbers after the schema's defaults, expressions, the experiment variant and the user's knobs, so your UI can show exactly what was applied.
  • experiment is present when the user is in a running experiment, and holdout: true when they are in the holdout.
  • rec_id names this exact list for one minute. Keep it if you want to explain the list.

Hydrate the returned ids from your own database, as you already do. If WALRUS errors or times out, serve your previous query (newest, most popular). Never let a feed be empty because the sidecar is unavailable.

Knobs in your UI

  • Render each knob as a slider with the two ends labelled exactly as the schema's label reads. Never show signal names or weights.
  • Put presets as buttons above the sliders. Moving a slider deselects the preset.
  • Re-fetch the feed on every slider change with knobs in the request. The re-score takes a few milliseconds, so the feed should visibly reorder while the user drags.
  • Put the panel one tap from the feed. A control nobody finds is the same as no control.

Explain

GET /v1/recommendations/{rec_id}/explain/{item} answers from the stored list, not a recomputation, so the breakdown is the one that produced the score and always adds up to it. Each signal that contributed says in words what it found, using the actual items, genres and numbers involved. The one-line reason in a recommend response joins the two strongest, the second only when it carries real weight. 

{
  "rec_id": "rec_1a7751f9b1bde656", "item": "paranoid", "position": 1, "score": 0.678,
  "breakdown": [
    { "signal": "co_listed",   "value": 0.267, "because": "Often added to playlists with Back in Black" },
    { "signal": "sounds_like", "value": 0.218, "because": "Close to Thunderstruck in energy and valence" },
    { "signal": "genre_fit",   "value": 0.050, "because": "Shares rock and hard rock with Back in Black" }
  ]
}

Turn the top entry into a sentence in your UI: "Because you liked Road bike". Attributes marked sensitive count in scoring and constraints but are never named in a reason. For platforms under the EU Digital Services Act, an explanation like this plus the knob panel is the basis for the Article 27 duties: the main parameters explained, and an option for the user to change them.

What is built

Entities and interactions are stored in memory today, so they are lost when the engine restarts. Recommend ranks from that store, which is built from the whole catalogue and suits catalogues of a few thousand items. Neo4j persistence is the target design.

Anything a schema asks for that the engine does not do yet is skipped, never fatal, and listed under warnings when you push.

  • Signals: item_neighbors, co_occurrence, attribute_target, global_count, low_exposure, age_decay, context_match, provided, user_neighbors, proximity and embedding.
  • Candidate sources: item_neighbors, co_occurrence, user_neighbors, factors, popular and fresh. With none declared, every item of the type.
  • Constraints: every form, including within_km, interacted, and operands from $user, $context and $seed.
  • Rules: attribute quotas (max per per positions).
  • Similarity metrics: jaccard, cosine, equals, log_ratio and closeness.
  • Not yet: trend, own_history, satiation, recurrence, formula, attribute_match, attribute_value, sequence, mutual_connections, diversity re-ranking, mix, group, reciprocal (two-sided matching), and the place, cap and pin rules.

Instant re-rank

Everything that does not depend on weights (the candidates, the hard constraints, the similarities between candidates and seed items, co-listing counts and taste profiles) is computed once and kept as a snapshot. Moving a knob changes only weights, so the next request reuses the snapshot and only re-scores. Any write to the store starts a new snapshot, so nothing is ranked from stale data.

Learned taste

The embedding signal learns item vectors from the interactions, in the background: call POST /v1/models/train, or set WALRUS_TRAIN_INTERVAL (for example 15m) to retrain on a schedule. A user's own vector is solved from their history on every request, so what they did a minute ago counts at once; items added after the last run score neutrally until the next one. Until the first run the signal scores every item alike. After you change a training setting in the schema, GET /v1/models shows retrain_pending and the old model keeps serving until you train again.
